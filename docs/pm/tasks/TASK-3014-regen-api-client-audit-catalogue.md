## Description
Wire the new API surface through the toolchain: regenerate the OpenAPI-driven
`@openbucket/api-client` so the console gets typed `rotateKey`/`revokeKey`/
`getKeyEffectivePermissions`/`simulateKeyAction` methods and the new `scope`
fields, and register the two new audit events in the `AuditService` catalogue so
downstream log tooling recognizes them.

## Files to create / modify
- `libs/api-client/src/lib/api/keys-admin.service.ts` — regenerate (adds the four methods).
- `libs/api-client/src/lib/api/keys-admin.serviceInterface.ts` — regenerate.
- `libs/api-client/src/lib/model/{created-key-dto,key-summary-dto,create-key-dto}.ts` — regenerate (add `scope`).
- `libs/api-client/src/lib/model/{rotated-key-dto,key-scope-dto,effective-permissions-dto,simulate-request-dto,simulate-response-dto}.ts` — new (generated).
- `libs/api-client/src/lib/model/models.ts` — regenerate (barrel).
- `libs/nestjs/src/lib/admin/audit/audit.service.ts` — modify. Add `key.rotated` and `key.revoked` to the catalogue doc table.
- `docs/ARCHITECTURE.md` (or the OpenAPI/whitepaper §5.7 section) — modify. Note the new key-management routes if that surface is documented there.

## Implementation notes
- The api-client is **generated**, not hand-written — the header in `keys-admin.service.ts` says "auto generated by OpenAPI Generator … Do not edit the class manually" and `libs/api-client/src/lib/.openapi-generator-ignore` governs overrides. Regenerate from the NestJS OpenAPI document (the same pipeline that produced the current `createKey`/`updateKey`/`deleteKey` methods), do not edit models by hand. Confirm the generator emits `KeyScopeDto`/`EffectivePermissionsDto` from the nestjs-zod DTOs' Swagger schemas (`createZodDto` feeds `@nestjs/swagger`).
- Verify the four new `operationId`s from [TASK-3010]/[TASK-3012] (`rotateKey`, `revokeKey`, `getKeyEffectivePermissions`, `simulateKeyAction`) appear as methods on `KeysAdminService` and its interface, and that `CreatedKeyDto`/`KeySummaryDto` now carry an optional `scope`.
- Audit catalogue: append two rows to the table in `audit.service.ts` (the canonical v1 catalogue callers must use), keeping the existing format:
  `| `key.rotated` | access key secret rolled | `subject`, `keyId` |`
  `| `key.revoked` | access key revoked (disabled) | `subject`, `keyId` |`
  These names are already emitted by [TASK-3010]; this task makes the doc authoritative so downstream indexing doesn't drop them.
- Security: regeneration must not widen the client's surface beyond the admin routes; the client carries no secrets (JWT is attached via the existing `withCredentials`/interceptor config, `api.base.service.ts`). Confirm the generated `simulateKeyAction`/`getKeyEffectivePermissions` are typed read-only (GET/POST returning DTOs) and don't accidentally expose `secretHash` — the response DTOs from [TASK-3011]/[TASK-3012] never include it.
- Keep the generated `git_push.sh`/`.gitignore` scaffolding untouched; only commit the regenerated TS.
